# Архитектура TG Bot

**Версия проектирования:** 1.0, 10 ноября 2026 года.
**Состояние:** спецификация, не описание уже существующего работающего кода.
**Связанный план:** [ROADMAP.md](ROADMAP.md).

## 1. Цель, границы и словарь

Создать **одного Telegram-персонажа**, который:
1. Пишет через подключённую LLM, ведёт диалог в нескольких личных и групповых чатах.
2. Получает в контекст **последние 20 сообщений конкретного диалога** плюс релевантные долгосрочные сведения.
3. Распознаёт присланные фото через поддерживающую изображения модель.
4. Имеет **одну общую долговременную память на все чаты** — намеренное отсутствие изоляции воспоминаний между собеседниками.
5. Сам извлекает воспоминания и объединяет похожие с помощью трёх «гномиков».
6. Имеет отдельную, редактируемую владельцем базу знаний с постоянной и поисковой активацией.
7. При некоторых событиях решает, написать ли сам, и при необходимости отправляет сообщение.

**Термины:** «говоритель» — модель ответа; «запоминатель» — извлечение фактов; «судья» — обработка похожих записей; «воспоминания» — автоматически накопленные факты; «база знаний» — записи, внесённые владельцем; «история» — исходные сообщения; «инициатива» — сообщение без нового входящего обращения; «задача» — работа, сохраняемая в очереди до выполнения.

Система **не** предназначена для нескольких персонажей, голосовых сообщений, автоматизации личного аккаунта, слежения за людьми или бесконтрольной рассылки. Команд управления памятью в Telegram не будет. Стандартное первоначальное действие Telegram «Начать» допустимо, так как оно необходимо для установления личного диалога с ботом.

## 2. Основные принципы

1. **Единая личность:** в приложении существует ровно одна конфигурация характера и один общий набор воспоминаний.
2. **Отдельные текущие диалоги:** история и очередность ответов определяются по паре «чат + тема»; память при поиске общая. Telegram-пользователь имеет стабильный числовой идентификатор независимо от отображаемого имени.
3. **Никаких секретов в Git:** токены Telegram и API-ключи остаются в локальном защищённом окружении; в репозитории — только примеры без секретов.
4. **Код проверяет права и состояние:** модель может предлагать текст и решения, но не изменять напрямую базу знаний или настройки доставки.
5. **Ответ важнее фоновой работы:** запоминатель, судья и инициативные пробуждения не блокируют ответы пользователя.
6. **Никакого бесконечного повтора:** все фоновые действия ограничены по времени и числу повторов; ошибки логируются, задачи сохраняются.
7. **Проверка от интерфейса до результата:** не считать функцию готовой, если существует только код, тест или удачный ответ модели.

## 3. Состав компонентов

**Telegram-приёмник (aiogram):** принимает обновления через long polling в единственном процессе, различает личный чат, группу, супергруппу и тему, извлекает сообщение и фото, отмечает уникальные обновления.

**Реестр чатов и участников:** хранит разрешённые чаты, последний контакт и доступность отправки; определяет пользователя по Telegram ID, а не по имени. Поддерживает отключение инициативы и всех ответов для конкретного чата административной настройкой.

**Обработчик диалога:** сохраняет входящий материал, строит запрос говорителя, ждёт API, безопасно отправляет ответ, сохраняет фактический результат отправки. Порядок сообщений внутри одного диалога сохраняется; два разных чата не смешивают текущую историю.

**Сборщик контекста:** составляет системные инструкции из выбранной личности и базы знаний, последние 20 сообщений своего чата, найденные записи общей памяти. Ограничивает размер токенов; при нехватке места сокращает поисковый контекст, но не начинает незаметно подмешивать другой чат.

**Менеджер LLM:** маршрутизирует текстовые, визуальные и embedding-запросы; задаёт таймауты, предел одновременных вызовов, повторы только при корректных причинах; учитывает лимиты провайдера. Допускается один API для всех гномиков. Модель без зрения не объявляется визуальной.

**Хранилище:** SQLite в режиме WAL, внешние ключи, последовательные миграции, транзакции. Отдельные таблицы истории, воспоминаний, базы знаний, заданий, состояния инициативы, логов. «Отдельная база знаний» означает логически отдельный набор записей и доступов, не обязательный второй файл БД.

**Фоновый исполнитель:** долговременная очередь для запоминателя, судьи и инициативных событий. Событие создано → ожидает → выполняется → завершено/повтор/ошибка. При перезапуске невыполненные задания восстанавливаются.

**Планировщик инициативы:** создаёт события пробуждения, проверяет разрешение писать, лимиты и время тишины; решение о сообщении принимает LLM, фактическую отправку разрешает код.

**Диагностика и обслуживание:** структурированные события, метрики, резервные копии; локальные инструменты владельца для просмотра/редактирования базы знаний, удаления записей и отключения инициативы. Не нужно создавать веб-панель до появления работающих основных функций.

Схема потока:

    Telegram → приёмник → идентификатор чата/темы → история SQLite
                                         ↓
                                     говоритель
                                         ↑
                            сборщик контекста
                      ↗ база знаний    ↖ общие воспоминания
                                         ↓
                                  менеджер LLM
                                         ↓
                               Telegram + история
                                         ↓
                        счётчик новых сообщений
                                         ↓
                           очередь → запоминатель
                                           ↓
                                 новое воспоминание
                                           ↓
                              поиск схожих векторов
                                           ↓
                                судья (если >= 0,90)

    планировщик → событие инициативы → проверка ограничений
                → решение LLM → говоритель → Telegram

## 4. Telegram: события, запуск и ответы

- Первое личное сообщение должен прислать пользователь: Bot API не позволяет боту начинать неизвестный личный чат. Никакой «пользовательский Telegram-аккаунт» для обхода не используется.
- В группах для обычной фоновой беседы требуется нужный режим видимости. С включённым Privacy Mode бот получает не всю переписку. Боты обычно не получают сообщений других ботов.
- Приём группы не означает ответ на каждое сообщение. Исходная политика: в личном чате отвечать на входящее содержательное сообщение; в группе — на прямое обращение/упоминание/ответ на реплику бота, иногда на очевидное обращение по имени; остальные доступные сообщения учитывать в истории и запоминании. Условия уточняются и тестируются в фазе 2.
- Служебные события (вход/выход участников, закрепление и др.) не увеличивают счётчик 20 сообщений, если специально не определено иное.
- У сообщения фиксировать Telegram chat_id, message_id, from_user.id, дату, тип, текст, ответ на сообщение, message_thread_id (если есть). Различать сообщения реального человека и ответ бота.
- Один уникальный ключ для входящих сообщений: chat_id + message_id; повторно доставленный update не должен создавать второй разговор и второе воспоминание.
- Для форумных тем контекст и последовательность ответов локальны к (chat_id, message_thread_id). При отсутствии темы используется «основной диалог».
- При редактировании сообщения можно обновить его текст и отметить изменённость, но модель уже могла прочитать первоначальную версию. Автоматическое удаление из памяти при удалении исходного сообщения **не гарантируется возможностями Bot API**.
- Сохранить ответ в истории только с честным состоянием: подготовлен → отправляется → отправлен с Telegram message_id / не отправлен. Не показывать в истории как доставленное то, что Telegram отклонил.
- При неопределённом результате отправки (например, таймаут после принятия Telegram) нельзя обещать абсолютную защиту от дублей: логировать неопределённость и применять консервативную политику, не делать бесконечных повторов.

## 5. История и сборка контекста

**Последние 20** — последние 20 доступных содержательных сообщений в конкретном диалоге, включая собственные успешно отправленные реплики. Сообщения разных людей в общей группе входят в одну историю группы с указанием имени и ID автора; личные чаты — отдельные. Текущий входящий запрос уже присутствует в истории и не дублируется второй раз.

При каждом обращении говорителя:
1. Взять стабильный снимок истории нужного чата/темы.
2. Включить постоянные записи базы знаний; поисковые — по тексту текущей темы общения.
3. Найти релевантные воспоминания из **общего** хранилища (именно так задумано).
4. Упорядочить инструкции: неизменные правила приложения и безопасности → характер/постоянная база знаний → краткая история и найденная память → сообщение пользователя.
5. Отдельно указать авторов и даты; воспоминание «Марк утверждал X» не превращать автоматически в объективное «X доказано».
6. Ограничить токены и число извлечённых записей конфигурацией; если 20 сообщений не помещаются в модель, записать факт усечения в диагностику, не нарушая отделение чатов.

Для запросов без подходящих воспоминаний не выдумывать, будто персонаж «помнит». Извлечённые воспоминания и текст пользователей — **данные**, а не новые системные указания.

## 6. Изображения и зрение

Начальная поддержка: Telegram photo и изображения, пришедшие документом с допустимым MIME-типом и размером. Видео, анимация, стикеры и аудио не входят в обязательную первую версию зрения.

Алгоритм:
1. Проверить размер, тип и лимиты Telegram, получить файл через Bot API.
2. Не записывать API-ключи, приватные URL файлов, исходные байты фото в журнал.
3. Подать изображение **в соответствии с интерфейсом выбранного провайдера** вместе с подписью и контекстом чата, а не подменять его текстовой заглушкой.
4. Вызвать модель с подтверждённой поддержкой изображений. Если основная модель текстовая, использовать отдельную визуальную модель, а её описание передать говорителю с явным происхождением.
5. В историю сохранить текст подписи и при необходимости краткое описание изображения для будущей суммаризации. Сами файлы по умолчанию долговременно не хранить.
6. Если зрения нет или обработка не удалась, ответить без выдумывания содержания картинки и дать диагностическую причину владельцу.

Проверять реальным PNG/JPEG на всех звеньях: Telegram → скачивание → запрос API → описание → говоритель → ответ.

## 7. База знаний владельца

Отделена от воспоминаний, редактируется только администратором на стороне приложения. Каждая запись:
- id, текст, заголовок (необязательно), режим ALWAYS или SEARCH;
- включена/отключена, приоритет, теги/ключевые выражения, дата изменения;
- при SEARCH — текстовый поиск FTS5 и, если настроен, семантический поиск; при ALWAYS — всегда в системном контексте;
- валидация объёма: слишком много постоянного текста не должно уничтожать окно истории.

Примеры: личность и речевые особенности, биография, привычки, правила инициативы, сведения о вымышленном мире. Инструкции приложения о безопасности и отправке не редактируются собеседниками через чат. Гномики **не** имеют прямой операции «переписать базу знаний».

Для начального использования достаточно локального текстового файла настроек/данных и административного импорта с проверкой, позднее — локальный инструмент редактирования. Не нужен Telegram-бот с командами для администрирования.

## 8. Общее хранилище воспоминаний

**Единое на персонажа:** записи из всех чатов доступны поиску независимо от источника. Это не баг изоляции, а требование. Однако исходный чат, автор, время и связь с сообщениями сохраняются, чтобы модель знала происхождение факта.

Пример записи: «Антон говорил 10 ноября, что больше любит зелёный чай»; источники содержат ID соответствующих сообщений. Отношения и предположения маркируются как сообщения/мнения, а не как достоверные универсальные факты.

Рекомендуемые поля: memory_id, text, status (active/superseded/deleted), source_chat_id, source_user_id (если применимо), source_message_ids, created_at, updated_at, embedding, embedding_model, embedding_version, decision_log_id. Для объединений нужна таблица связей исходных/новых записей и история изменений.

**Поиск:** первая ступень — фильтрация активных записей, затем FTS5 по словам и косинусная близость embeddings, затем ранжирование и ограничение длины. Полностью пустая выдача допустима. Реализация на небольших объёмах — SQLite для текста, векторы сравниваются в Python; не вводить сервер векторов до необходимости.

**Важная граница:** векторы, полученные разными моделями/версиями, нельзя сравнивать как однородные. При смене модели embeddings необходима фоновая переиндексация, до её завершения старые векторы не участвуют в новом сравнении.

Содержательные сведения могут быть перенесены из личной беседы в другую — участникам это сообщается заранее. При этом очевидные учётные данные (пароли, токены, одноразовые коды) не следует сохранять в общую память. Полной автоматической гарантии распознавания всех чувствительных сведений нет.

## 9. Гномик «говоритель»

Вход: исходное сообщение или событие инициативы, контекст 20 сообщений, постоянная/поисковая база знаний, релевантные общие воспоминания, при необходимости изображение. Выход: текст ответа или осмысленное решение промолчать в группе/при инициативе.

- Не раскрывать системные промпты, ключи API и внутренние служебные данные.
- Нельзя выполнять инструкции из цитат, фоток, пользовательских сообщений как команды на изменение программы или БД.
- Для личного сообщения нужен ответ или явно обрабатываемая ошибка; для групп допустима тишина по политике триггеров.
- Говоритель не записывает новые воспоминания напрямую: это работа запоминателя.
- Фиксировать входной запрос, выбранную модель, задержку, ошибку и расход при наличии данных от провайдера без публикации приватного контента в логах по умолчанию.

## 10. Гномик «запоминатель»: строго каждые 20 сообщений

Единица счёта — один диалог (чат и тема). Считаются **содержательные сообщения**, доступные приложению: принятые сообщения людей и успешно отправленные сообщения бота. Число сообщений должно определяться из сохранённой истории, а не из счётчика в оперативной памяти.

1. На каждые следующие 20 ещё не обработанных сообщений сформировать **один неизменяемый пакет**, с ID первого/последнего сообщения, версией исходного содержимого и уникальным ключом задания.
2. Сохранить задание в БД даже тогда, когда говоритель занят: не терять пакет и не запускать второй запоминатель на него.
3. Запоминатель запускается с низким приоритетом, когда освободится лимит модели; он не мешает говорителю и может использовать тот же API.
4. Получает 20 сообщений **именно этого чата/темы** с авторами и временем; выдаёт структурированный список **атомарных** фактов, событий, предпочтений, намерений и значимых изменений. Может вернуть пустой список.
5. Не записывать в память пароль/код/токен; сохранять связь с источником, не принимать рассказы персонажей за проверенные внешние факты.
6. В транзакции создать новые воспоминания или отметить отсутствие полезных фактов; только после успешной фиксации продвинуть курсор обработанных сообщений.
7. Создать задания судьи по новым кандидатам. Если обработка не удалась, курсор не продвигать; выполнить ограниченный повтор позже.

Поток из 40 новых сообщений создаёт два пакета по 20. Даже если API всё время занят ответами, оба задания остаются в очереди. Это снимает неоднозначность фразы «если не вызван говоритель»: **задание не теряется, просто ждёт свободного слота**. Если по ошибке получен пересекающийся пакет, уникальный ключ и транзакция не позволят удвоить воспоминания.

Для изображений в 20-сообщном пакете используется сохранённое описание с указанием, что это результат зрения, а не оригинальный текст пользователя.

## 11. Гномик «судья»

При **каждом новом воспоминании**:
1. Вычислить embedding тем же утверждённым способом, что для остальных активных записей.
2. Найти ближайших соседей из **общей** памяти. Исключить саму запись, удалённые записи, записи с несовместимой моделью embeddings.
3. При косинусной близости **>= 0,90** хотя бы с одним соседом поставить задачу судье с исходной новой записью и ограниченным числом найденных кандидатов. Порог настраиваемый, 0,90 — начальное значение, не «90% одинакового смысла».
4. LLM выбирает одно из решений: оставить отдельно, объединить/переформулировать, разделить на несколько атомарных фактов, отклонить повтор. Решение должно содержать идентификаторы исходных записей и итоговый список фактов.
5. Программная проверка: никаких внешних несуществующих источников, недопустимых ID, пустого необоснованного удаления, текстовых инструкций на изменение БД. Противоречивые по времени/автору факты не сливать слепо.
6. В транзакции записать итог, связи с исходниками, версии, векторы; сделать прежние записи неактивными только при подтверждённом замещении. Сохранить историю решения для отката.
7. В случае ошибки **оставить новые и старые факты**; пропуск или падение судьи не должны вести к потере памяти.

Судья работает по низкоприоритетной очереди. При конкурентном поступлении фактов использовать захват задачи и сериализацию записи, чтобы два решения не заменили одну запись несовместимым образом.

## 12. Менеджер ИИ и порядок запросов

Конфигурация содержит по назначению: провайдер, адрес API, модель, тип задачи, поддержка изображений, embedding-модель, таймаут, лимит параллелизма и бюджета. Секреты читаются из окружения и не сохраняются в логах.

Приоритеты по умолчанию:
1. Ответы на новые личные и адресованные сообщения.
2. Продолжение уже начатого ответа/безопасное завершение отправки.
3. Решение/ответ инициативы, если не истёк смысл события.
4. Запоминатель.
5. Судья и техническая переиндексация.

Для единственного API с параллелизмом 1 запросы выполняются последовательно. Для разных API могут использоваться отдельные ограничения, но **один чат** защищён от одновременных конфликтующих ответов. Живой входящий ответ может отложить очередной фоновый вызов, но не обрывает уже отправляемый HTTP-запрос без причины.

Повторять временные ошибки (429 с учётом Retry-After, таймаут подключения, часть 5xx) с конечным backoff; ошибки аутентификации/неподдерживаемого изображения не повторять без изменения условий. Если получен пустой, невалидный или оборванный ответ модели, выполнить ограниченную обработку ошибки и уведомить диагностикой, не запускать бесконечные циклы.

## 13. Инициатива

Принцип: **программный сигнал решает, когда проверить возможность, LLM решает, стоит ли писать; программа проверяет право отправки**.

Начальные сигналы:
- прошло заданное время без общения в конкретном чате;
- LLM после диалога предложила вернуться к теме через допустимый интервал;
- отложенный повод из прошлой беседы (только если его можно проверить по сохранённому событию).

Отдельного «четвёртого гномика» не требуется: решение — короткий вызов говорителя или его компактного режима. Модель возвращает структурированное решение «писать / не писать», текст или запрос на генерацию, и время следующей проверки в разумных пределах. Следующее пробуждение хранится в БД.

Обязательные проверки кода **до** обращения к LLM и **до** отправки:
- чат уже существует и бот вправе в него писать;
- инициатива в этом чате разрешена владельцем; для личного чата пользователь хотя бы раз начал разговор;
- нет активного входящего сообщения, на которое надо ответить;
- сейчас разрешённые часы с учётом часового пояса;
- соблюдены кулдаун и дневной лимит; одинаковые сообщения не повторяются;
- у чата нет блокировки/ошибки Forbidden; группе не мешают активные ограничения;
- инициатива никогда не создаёт рассылку в неизвестные чаты.

Первоначально **инициатива по умолчанию выключена**, пока владелец не проверит обычную переписку и не разрешит её для конкретного чата. В дальнейшем пользователь может попросить обычными словами «не пиши мне сам»; распознавание такого запроса должно создавать устойчивый запрет на инициативу, без требования команды. До реализации такого понимания запрет можно выставлять владельцем вручную; человек всегда может заблокировать бота.

Для групп инициатива изначально выключена, включается отдельно. Не ставить пробуждения чаще минимального интервала, исключить циклическое «пишу сам → это новое сообщение → пишу сам». Собственное инициативное сообщение может учитываться в истории/пакете запоминателя, но не считается новым поводом инициативы.

## 14. Структура данных и транзакции

Минимальные логические таблицы (имена окончательно выбрать при первой миграции):

| Набор | Ключевые данные | Когда нужен |
|---|---|---|
| chats | chat_id, тип, заголовок, режим, разрешение ответов, инициатива, часовой пояс | фаза 1–2 |
| users | telegram_user_id, имя для отображения, изменения имени | фаза 2 |
| messages | chat_id, thread_id, telegram_message_id, автор, роль, дата, текст, тип, описание изображения, статус отправки | фаза 1–3 |
| conversation_cursors | chat_id, thread_id, граница обработанных 20 сообщений | фаза 5 |
| knowledge_entries | текст, ALWAYS/SEARCH, приоритет, включено, временные метки | фаза 4 |
| memories | текст, статус, источник, версии, эмбеддинг и его модель | фаза 5–6 |
| memory_sources / memory_revisions | связи с исходными сообщениями, версии и объединения | фаза 5–6 |
| jobs | тип, уникальный ключ, параметры, статус, попытки, следующая попытка, lease | фаза 5 |
| initiative_state | следующее пробуждение, последний выход, кулдаун, дневная квота, запрет | фаза 7 |
| execution_log | тип операции, чат, модель, длительность, код ошибки без секретов | фаза 1–8 |

Таблицы создаются **по мере появления потребителя**. Не создавать весь каркас с мёртвыми полями заранее. Для сообщений важно, что идентификатор Telegram может быть разным между чатами; первичный ключ приложения независим от него.

**Транзакционные границы:**
- входящий update → проверка уникальности → сохранение сообщения;
- формирование задания запоминания + уникальный ключ диапазона в одной транзакции;
- запись воспоминаний + продвижение курсора пакета в одной транзакции;
- решение судьи + деактивация исходников + новые векторы + история версий в одной транзакции;
- резервирование события инициативы до отправки и фиксация результата после отправки.

SQLite должен иметь индексы по чату/времени, задаче/состоянию, памяти/статусу и FTS5 для текста. Внешние ключи — включены. Доступ к БД сериализуется и выполняется короткими транзакциями; не держать транзакцию открытой во время вызова LLM.

## 15. Ошибки, устойчивость и проверки

- Прерывание процесса после принятия сообщения: после перезапуска оно остаётся в истории, не удваивается при повторном update.
- Зависший API: есть таймаут и диагностический результат; очередь новых сообщений не должна молча навсегда остановиться.
- Задание памяти упало: не продвинут курсор, оно повторяется ограниченное число раз.
- Судья ответил неправильно: нет удаления исходных записей без подтверждённой транзакции.
- Telegram отклонил отправку: отметить ошибку и остановить инициативу для недоступного чата.
- Изображение неподдерживаемо: не утверждать, будто оно было распознано.
- Неподходящая версия embeddings: требовать переиндексации, не сравнивать разнородные векторы.
- Исключить секреты из вывода ошибок, коммитов, системных логов.
- Логирование структурировано: тип события, chat_id, job_id, provider/model, длительность, код/тип ошибки; полный текст переписки по умолчанию не журналировать.

Тесты по уровням: модульные (чистая логика), интеграционные (SQLite, fake API), системные (тестовый Telegram-бот и настоящий провайдер), сценарии после перезапуска. Системные тесты не заменять имитацией с зелёным CI.

## 16. Конфиденциальность и эксплуатационные границы

Между чатами **нет жёсткой приватной перегородки воспоминаний**. Персонаж может вспомнить сказанное одним другом в другом чате. Это должно быть понятно всем участникам *до* использования. Нельзя обещать конфиденциальность личных разговоров внутри памяти персонажа.

При этом:
- по возможности не сохранять явные пароли, API-ключи и одноразовые коды в память; технические логи должны быть очищены от секретов;
- не публиковать базу SQLite, журналы и резервные копии; хранить на доверенном компьютере;
- обеспечить локальный запрос владельцу на удаление истории/воспоминаний конкретного пользователя и полную очистку; при удалении производных записей учитывать объединённые воспоминания и резервные копии;
- не считать удаление сообщения в Telegram надёжным запросом удаления из БД;
- явным текстом предупредить о передаче сообщений и изображений внешнему LLM-провайдеру;
- не включать массовую инициативу без тестирования и лимитов.

## 18. Проверка соответствия требованиям

| Требование | Обязательная пользовательская проверка |
|---|---|
| Один персонаж в нескольких чатах | В двух разных личных чатах одинаковые характер и установки |
| История отдельно по чатам | Новое сообщение А не подмешивает последние 20 сообщений Б |
| Память общая | Сказанный в чате А безопасный факт извлекается в чате Б с указанием источника |
| Фото | Реальное изображение правильно описано в ответе |
| Запоминатель | После 20 и 40 сообщений возникают два непотерянных пакета |
| Судья | При схожести >= 0,90 вызов LLM, решение и история изменений; при сбое записи целы |
| База знаний | ALWAYS всегда присутствует, SEARCH появляется только по релевантности |
| Очередь | Фоновая нагрузка не блокирует своевременный ответ |
| Инициатива | В разрешённом чате пишет без входящего сообщения, соблюдая запрет и кулдаун |
| Перезапуск | История, память, незавершённые задания и следующий wake переживают рестарт |
