# План разработки TG Bot по фазам

**Версия:** 1.0, 10 ноября 2026 года.  
**Состояние:** только проектирование; ничего из фаз разработки не объявляется реализованным.
**Основная архитектура:** [ARCHITECTURE.md](ARCHITECTURE.md).

## 0. Правила выполнения плана

1. Разрабатывать **одного персонажа**. Не закладывать поддержку множества персонажей «на всякий случай».
2. У персонажа **общая долговременная память** во всех чатах; последние 20 сообщений — только из текущего чата/темы.
3. Без пользовательских команд для памяти, переключения персонажа или инициативы. Первичное открытие бота через стандартный интерфейс Telegram — отдельное техническое требование платформы.
4. Следующую фазу начинать **после проверки пользовательского сценария** предыдущей, а не просто после зелёных тестов.
5. Не реализовывать будущую фазу преждевременно, если её нельзя проверить без зависимостей. Не создавать пустые файлы и интерфейсы ради видимой структуры.
6. В каждой фазе: изучить текущее состояние → внести минимальное изменение → провести модульную/интеграционную проверку → проверить путь в Telegram → задокументировать результат.
7. Если реальные Telegram или API недоступны, ставить статус **НЕ ПРОВЕРЕНО**, а не «готово».
8. Не подменять проверку исправлением тестов ради зелёного цвета. Изменять неверный тест только с объяснением причины.
9. Никогда не коммитить токены и личные переписки. Все сообщения пользователю, документация и инструкции — на русском; имена Python-библиотек, ключи конфигурации и API остаются техническими идентификаторами.

## 1. Карта зависимостей

    P0  Согласовать спецификацию (документы)
     ↓
    P1  Один бот, Telegram ↔ LLM ↔ Telegram
     ↓
    P2  Надёжные несколько чатов + отдельная история каждого
     ↓
    P3  Настоящее зрение (фото → модель → ответ)
     ↓
    P4  Отдельная база знаний ALWAYS/SEARCH
     ↓
    P5  Общие воспоминания + эмбеддинги + запоминатель
     ↓
    P6  Судья и безопасное объединение воспоминаний
     ↓
    P7  Инициатива и самостоятельная отправка
     ↓
    P8  Эксплуатация, восстановление, удаление данных и итоговая приёмка

Почему именно так:
- Запоминатель требует **историю и достоверные ID сообщений** из P2.
- Чтобы изображения не исчезали из смысловой памяти, сначала нужен **визуальный контент и его текстовое описание** из P3.
- До смешивания автоматической памяти и инструкций нужно отдельно проверить **базу знаний** из P4.
- Судья не существует без работающих воспоминаний, эмбеддингов, транзакций и очереди из P5.
- Инициатива требует устойчивой истории, модели, отслеживания доступности чатов и очереди, поэтому идёт после памяти.
- Сбои и восстановление тестируются на каждой фазе; P8 — не отсрочка основных мер безопасности, а финальная сквозная проверка и инструменты обслуживания.

План **последовательный**. Маленькую подготовку общего компонента можно сделать раньше только тогда, когда она необходима для текущей фазы и сразу проверяется.

## P1. Минимальный рабочий Telegram-бот

**Зависимости:** P0.  
**Цель:** первое настоящее сообщение Telegram → запрос к модели → ответ Telegram.

Реализовать только:
1. Python-проект с фиксированными рабочими зависимостями, одной точкой запуска и минимальной конфигурацией через окружение.
2. Чтение токена Telegram и ключа/адреса/модели LLM; проверка отсутствия обязательных настроек без вывода секретов.
3. Подключение aiogram 3 через long polling: один процесс на токен, корректное завершение.
4. Обработчик личного текстового сообщения. Роль персонажа — одна настройка, без переключений и команд управления.
5. HTTP-адаптер LLM с таймаутом и понятной диагностикой 401/429/5xx; ответ в тот же чат.
6. Сохранение базовой истории входящих/отправленных сообщений в SQLite, миграция первой версии, уникальность (chat_id, telegram_message_id).
7. Достаточные логи без полного текста переписки и без ключей; файл-пример настроек и инструкции запуска на Windows.

**Не делать:** embeddings, судью, инициативу, изображение, полноценный групповой диалог, административную панель.

**Приёмка на живом Telegram:**
- [ ] Пользователь начинает диалог, отправляет «Привет», бот отвечает осмысленным текстом через настоящий API.
- [ ] Следующее сообщение содержит связное продолжение, а не только изолированный ответ.
- [ ] Перезапуск приложения сохраняет историю и не раскрывает токен.
- [ ] Неверный API-ключ вызывает диагностируемую ошибку, а не зависание.
- [ ] Успешная отправка зафиксирована с Telegram message_id, неудачная не помечена доставленной.

**Статус: НЕ РЕАЛИЗОВАНО.**

## P2. Несколько личных и групповых чатов, контекст 20 сообщений

**Зависимости:** P1.  
**Цель:** текущие разговоры не смешиваются, один персонаж может общаться в разных местах.

Реализовать:
1. Нормализованные chat_id, user_id, необязательный message_thread_id, имена авторов, ответ на сообщение.
2. Получение последних **20 содержательных сообщений данного чата/темы**, включая исходящий текст бота; автора группы передавать явно.
3. Сериализацию ответов внутри одного чата/темы; разрешить обработку разных чатов с общим лимитом API.
4. Политику группового ответа: прямое упоминание, ответ на реплику бота или явно адресованная фраза. Не отвечать на каждый разговор в группе.
5. Обработку повторных Telegram updates, редактированных сообщений (без обещаний исправить уже отправленные ответы), заблокированных чатов, вступления/выхода.
6. Фиксацию того, что сообщения группы доступны только согласно действующей настройке Privacy Mode; инструкция владельцу по настройке.
7. Сохранение истории после перезапуска и корректную сборку контекста с ограничением токенов.

**Не делать:** общие воспоминания — они появятся в P5. В P2 проверяется **разделение краткосрочной истории**, а не изоляция будущей общей памяти.

**Приёмка:**
- [ ] Друг А и друг Б пишут одновременно: каждый получает ответ в свой чат.
- [ ] В разговор Б не попадает двадцатка сообщений из А.
- [ ] В группе бот понимает автора и отвечает на обращение, но молчит при случайной переписке других людей.
- [ ] В супергруппе с темами сообщения не перемешиваются между темами.
- [ ] Повтор update не создаёт дубли истории и вторые ответы без оснований.
- [ ] Перезапуск сохраняет порядок и контекст.

**Статус: НЕ РЕАЛИЗОВАНО.**

## P3. Зрение: обработка изображений

**Зависимости:** P2.  
**Цель:** персонаж видит реальные фотографии, а не предполагает их содержание.

Реализовать:
1. Приём Telegram photo; при технической необходимости — image/jpeg и image/png в документах.
2. Проверку типа, размера, скачивание через Telegram Bot API, временную обработку без постоянного сохранения файлов по умолчанию.
3. Адаптер к API модели с image input; при разных моделях разделить визуальную интерпретацию и финальный ответ говорителя.
4. Подачу изображения и текста пользователя в единый ответ; сохранение текстового описания изображения с указанием источника для будущей памяти.
5. Ошибки «модель не поддерживает картинки», «файл не скачан», «API вернул ошибку» без выдуманного анализа изображения.

**Приёмка:**
- [ ] Реальное фото с известным проверяющему содержимым → бот верно указывает видимые объекты.
- [ ] Фото и вопрос «что на картинке?» попадают в **один** осмысленный ответ.
- [ ] В неподдерживаемой модели изображение не теряется молча; ошибка понятна.
- [ ] Текстовый разговор после фото не ломается, история не раздувается байтами изображений.
- [ ] Проверено, что передаются реальные байты/предусмотренная провайдером структура изображения, а не только его URL или имя.

**Статус: НЕ РЕАЛИЗОВАНО.**

## P4. Постоянная и поисковая база знаний

**Зависимости:** P2, P3 для полноценного контекста с фото.  
**Цель:** владелец задаёт характер, инструкции, мир и сведения отдельно от автоматически накопленной памяти.

Реализовать:
1. Записи с id, текстом, режимом ALWAYS или SEARCH, флагом включения, приоритетом и датами.
2. Импорт владельцем через локальный файл/административный инструмент; не через публичные Telegram-команды.
3. Включение ALWAYS в системный контекст, SEARCH — только по релевантности текста/темы; сначала FTS5, семантический поиск позже без блокировки фазы.
4. Стабильный порядок инструкций, защита от «перепиши мои правила» из пользовательских сообщений и изображений.
5. Отключение записи и независимость от истории/воспоминаний.

**Приёмка:**
- [ ] Изменение стиля персонажа через базу знаний меняет ответы.
- [ ] Постоянный факт виден в нескольких чатах.
- [ ] Поисковый факт появляется по теме, а не при каждом сообщении.
- [ ] Выключенная запись не попадает в контекст.
- [ ] Участник Telegram не может переписать базу знаний текстом в чате.

**Статус: НЕ РЕАЛИЗОВАНО.**

## P5. Общая память и «запоминатель»

**Зависимости:** P2 (история), P3 (описания изображений), P4 (сборщик контекста).  
**Цель:** каждые 20 сообщений одного диалога выделяются воспоминания, которые затем доступны говорителю во **всех** чатах.

Реализовать:
1. Таблицы memories, memory_sources, embeddings и durable jobs с миграциями; курсор на каждый chat_id + thread_id.
2. Очередь низкоприоритетных заданий с сохранением после перезапуска. Уникальный ключ пакета по диапазону 20 сообщений.
3. Один пакет запоминателя ровно на **каждые следующие 20 содержательных сообщений чата**; считать входящие и успешно отправленные сообщения, не считать служебные updates.
4. Структурированный вывод запоминателя: 0..N атомарных фактов, источник, кто утверждал, когда; валидация JSON/схемы, пустая выдача допустима.
5. Векторизацию каждого итогового факта с фиксацией модели и её версии; полнотекстовый индекс.
6. Поиск общей памяти (текстовый + семантический) при формировании запроса говорителя.
7. Минимальные фильтры для очевидных паролей, кодов и токенов; никаких обещаний полной автоматической защиты чувствительных данных.
8. Транзакцию «факты сохранены → курсор пакета продвинут»; при ошибке курсор остаётся, задание повторяемо.
9. Приоритет живого ответа над памятью и отсутствие параллельных вызовов при лимите API 1.

**Приёмка:**
- [ ] После 19 сообщений задания нет; после 20 появляется **одно** задание; после 40 — второе.
- [ ] При непрерывном общении говорителя оба пакета ожидают, но не теряются.
- [ ] В чате А сообщить безопасный факт, дождаться его запоминания, в чате Б задать связанный вопрос; ответ использует **общую память**.
- [ ] Источник факта (кто и когда говорил) сохранён, оценка утверждения как факта/слуха не перепутана.
- [ ] Перезапуск до и после транзакции не порождает дубликатов и потерь.
- [ ] При ошибке эмбеддингов память не выдаёт бессмысленную близость.

**Статус: НЕ РЕАЛИЗОВАНО.**

## P6. «Судья» и версионность воспоминаний

**Зависимости:** P5.  
**Цель:** уменьшать дубли, не уничтожая важные различия и источники.

Реализовать:
1. Для каждой новой записи найти ближайшие активные факты **общего** хранилища.
2. При совместимых embeddings и косинусном сходстве >= 0,90 создать низкоприоритетное задание судьи (порог конфигурационный).
3. Судья может: оставить отдельно, слить, переформулировать, разделить, отбросить дубликат. Не ограничивать исход искусственным обязательным слиянием.
4. Строго проверить идентификаторы входа, выходную схему, исходные связи, противоречия и даты.
5. Транзакционно создать версии и новые векторы, отметить замещённые записи, сохранить возможность отката.
6. При ошибке/невалидном ответе **сохранить обе исходные записи**, вывести диагностику.
7. Не сравнивать разные embedding-модели без переиндексации; учесть повторные задания и конкуренцию.

**Приёмка:**
- [ ] Два практически одинаковых факта вызывают судью при реальном пороге.
- [ ] Несходные факты не вызывают лишний LLM-суд.
- [ ] Два противоположных утверждения от разных людей не превращаются в один ложный факт.
- [ ] Судья может разделить сложную запись на две с сохранением источников.
- [ ] Ошибка API посередине операции не удаляет исходную память.
- [ ] После перезапуска история изменений пригодна для диагностики.

**Статус: НЕ РЕАЛИЗОВАНО.**

## P7. Инициатива

**Зависимости:** P2 (чаты/доступ), P5 (очередь и память), P6 (устойчивое состояние воспоминаний).  
**Цель:** персонаж иногда пишет сам, но не спамит и не пишет незнакомым людям.

Реализовать:
1. Состояние инициативы отдельно по чату: разрешение, next_wake, последний контакт, последний исходящий, часовой пояс, дневная квота и пауза.
2. События: длительная тишина, отложенная договорённость или предложенный LLM допустимый следующий контакт.
3. Код предварительно проверяет ограничения, затем короткий вызов LLM принимает «писать/молчать», при необходимости говоритель формулирует текст.
4. Отправка только в ранее доступные чаты, с контролем Flood/Forbidden, времени тишины, кульдауна, повторов, активного ответа.
5. Инициатива для всех чатов сначала выключена, для групп включается отдельно.
6. Устойчивая запись next_wake и исхода отправки; после падения не создавать лавину «просроченных» инициатив.
7. Обычная человеческая фраза «не пиши мне первым» должна выключать будущую инициативу без специальной команды (надежность распознавания проверяется).
8. Не позволять собственному инициативному сообщению автоматически создавать следующую инициативу.

**Приёмка:**
- [ ] При известном чате, разрешении и событии персонаж отправляет сообщение без нового входящего.
- [ ] При решении «молчать» никакого сообщения нет, назначено следующее пробуждение.
- [ ] При выключенном разрешении, блокировке, часах тишины и лимите ничего не отправляется.
- [ ] Фраза «не пиши мне первым» устанавливает устойчивый запрет и работает после перезапуска.
- [ ] В группе инициатива не включается сама, в неизвестный личный чат отправок нет.
- [ ] После перезапуска нет двойной отправки по одному событию и нет лавины отложенных сообщений.

**Статус: НЕ РЕАЛИЗОВАНО.**

## P8. Итоговое качество и эксплуатация

**Зависимости:** P1–P7 проверены.  
**Цель:** приложение можно безопасно запускать и поддерживать на ПК владельца.

Реализовать:
1. Простой запуск на Windows и документацию: установка Python/зависимостей, создание бота, конфигурация API, запуск/остановка, хранение БД.
2. Резервные копии SQLite и практический тест восстановления; исключение ключей, истории и резервных копий из Git.
3. Локальные средства владельца: просмотреть/изменить записи базы знаний, заблокировать чат, выключить инициативу, удалить историю или воспоминания, очистить профиль пользователя, переиндексировать embeddings.
4. Систематизацию ошибок: Telegram, provider/model, vision, embedding, память, судья, инициатива, база.
5. Проверку лимитов, избыточных вызовов, бесконечных циклов и отсутствия мёртвых модулей.
6. При необходимости — запуск как фоновое приложение на доверенной машине. **Не** вводить веб-панель, Docker-кластер или VPS как обязательное условие.

**Итоговая приёмка:**
- [ ] Два друга и одна группа общаются с одним персонажем, ответы доставляются.
- [ ] Истории краткосрочно разделены, долгосрочная память намеренно общая.
- [ ] Фото реально распознаётся.
- [ ] Оба цикла «20 сообщений → запоминатель» и «похожий факт → судья» проходят.
- [ ] Постоянная/поисковая база знаний меняет ответы ожидаемо.
- [ ] Инициатива пишет самостоятельно и соблюдает запреты/лимиты.
- [ ] Прерванный процесс восстановлен без потери памяти и бесконечного повтора работ.
- [ ] Локальный инструмент удаляет выбранную информацию, включая производные данные по документированной политике; резервные копии учитываются.
- [ ] Предупреждение участникам об общей памяти и внешнем API реально предоставлено.
- [ ] Нет секретов в коммитах, диагностических текстах и сборочных артефактах.
- [ ] Выполнено ручное тестирование на **реальном** Telegram и реальном модельном API; его результаты записаны, а неподтверждённые сценарии помечены «НЕ ПРОВЕРЕНО».

## 3. Сценарии, которые нельзя пропускать

**Сценарий А — единая память, разные истории.**
Антон сообщает персонажу предпочтение в личном чате. Запоминатель сохраняет его в единой памяти. Марк в другом чате спрашивает о предпочтении Антона. Персонаж может использовать это воспоминание — это ожидаемое поведение. Но последние 20 сообщений Антона **не должны** подмешиваться в непосредственный контекст Марка.

**Сценарий Б — конфликт одновременно пришедших сообщений.**
Антон и Марк пишут в течение секунды. Обе записи сохраняются, последовательность ответов в каждом чате правильна, лимит единственного LLM API не нарушен. Ошибка у Антона не должна терять сообщение Марка.

**Сценарий В — два пакета запоминателя во время нагрузки.**
Говоритель занят, пока в одном чате накопилось 40 содержательных сообщений. Пакеты 1–20 и 21–40 существуют независимо и отрабатываются последовательно; ни один не исчезает.

**Сценарий Г — судья испортил ответ.**
Судья выдал некорректный JSON или сеть разорвалась посреди запроса. Оба исходных воспоминания остаются активными, задание имеет ограниченный повтор и диагностику.

**Сценарий Д — неожиданная отправка после перезапуска.**
Компьютер не работал сутки. После включения планировщик не отправляет десятки старых инициатив подряд; учитывает актуальное время, лимиты и разрешения.

**Сценарий Е — пользователь просит тишины.**
Друг пишет обычное сообщение «пожалуйста, не пиши мне сам». Запрет инициативы применяется устойчиво; обычные ответы на новые сообщения могут продолжаться, если не запрещены отдельно.

**Сценарий Ж — неподдерживаемая фотография.**
Бот не утверждает, будто видит изображение, если текущий провайдер отклонил его; владелец видит причину.

## 4. Шаблон отчёта о завершении каждой фазы

Каждая фаза заканчивается коротким отчётом в описании изменения или docs/reports/:

- **Фаза, дата, ветка, HEAD и перечень затронутых файлов.**
- **Реализованный путь:** действие пользователя → Telegram → обработчик → БД → API → результат → отображение.
- **Проверки:** какие тесты запускались, их вывод, какие живые сценарии проверены.
- **Ограничения:** что не работает, что **НЕ ПРОВЕРЕНО** и почему.
- **Регрессии:** какие предыдущие сценарии повторно проверены.
- **Решение:** фазу можно принять или нужно доработать. Следующая фаза не начинается при незавершённых обязательных критериях.

## 5. Риски и решения, обязательные до выполнения

- **Согласие участников.** Друзьям объяснить, что персонаж — ИИ и факты из одного чата могут попасть в другой. Заранее не обещать хранение секретов.
- **Приватность.** Не сохранять пароли, коды и токены в общую память намеренно; включить локальное удаление данных в P8. Это не абсолютная защита от раскрытия других сведений.
- **Стоимость API.** Запоминатель не требует отдельного провайдера, но всё равно расходует токены; ограничить бюджеты и максимальные размеры запросов.
- **Свойства embeddings.** Близость 0,90 зависит от модели и данных. Перед окончательным принятием судьи проверить на множестве реальных примеров.
- **Доступность.** На выключенном ПК long polling и инициатива не работают. Фоновый сервер — дальнейшее решение владельца.
- **Ограничения Telegram.** Нельзя начать неизвестную личную переписку; в группах видимость зависит от Privacy Mode; нельзя обещать синхронизацию всех удалений.
- **Неполная проверка.** Без Telegram-токена, работающего API и устройства/сервера невозможно подтвердить живую приёмку. Никогда не описывать такую фазу как полностью проверенную.

## 6. Контроль непреднамеренного расширения проекта

Следующее **не является частью плана** и не должно возникнуть незаметно:
- несколько персонажей, перенос конфигурации личности между персонажами;
- публичные команды Telegram и админ-бот;
- голос, TTS, распознавание аудио, видео;
- автоматизация обычного пользовательского Telegram-аккаунта;
- эмоциональный симулятор, сложные социальные агенты или самостоятельные внешние инструменты;
- микросервисы, распределённый кластер, обязательный внешний векторный сервер;
- логирование полной переписки в CI.

Добавлять это можно только после изменения требований и проверки зависимости от существующих функций.
